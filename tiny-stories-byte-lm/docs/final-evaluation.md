# The four required measurements, and the test split

`docs/experiment-design.md` asks for four measurements at each selected checkpoint and
reserves the untouched test split for final evaluation. This run fills all of them for
`checkpoint-00015752.pt`. Data in `reports/final-eval.json`, script
`scripts/evaluate_final.py`.

## 1. Strict UTF-8 validity, with an interval

```
120 samples × 400 generated bytes, temperature 0.8
valid 120/120 = 100.0%     Wilson 95% CI: 96.9% – 100.0%
```

The earlier curve in `gen-quality.jsonl` recorded "0% invalid from step 750 onward"
on **three samples per checkpoint**. At n=3 a single sample moves the rate by 33
points, so that row could not support the claim it appeared to make. At n=120 the
interval is the honest form of the statement: the true rate is below 3.1%, not equal
to zero.

## 2. UTF-8-legal next-byte probability mass

```
mean over 120 × 400 positions: 0.9999955   (5,475 ppm of the mass off the legal set)
```

The metric sums the model's own 256-way probability over the bytes the decoder still
accepts. Two readings matter:

- **It is already self-constrained.** Constrained decoding would recover 0.0005% of the
  mass, so it would change nothing — this is why no constrained sampler was built.
- **As a capability claim it is weak, and should not be sold as one.** The legal set
  contains all 128 ASCII bytes plus lead bytes, and the corpus is pure ASCII, so a model
  that simply stays inside ASCII scores ~1.0 without knowing anything about UTF-8. The
  number says "it does not wander into invalid bytes"; it does not say "it models
  UTF-8". Empirical validity (measurement 1) is the stronger statement of the two.

## 3. Word-level probability over the whole validation file

Entire file, 6,491,511 bytes, 1,266,259 words:

| quantity | validation | test |
|---|---:|---:|
| bytes | 6,491,511 | 6,437,958 |
| words | 1,266,259 | 1,256,522 |
| mean log probability per word | **−3.6993 nats** (5.34 bits) | −3.6931 nats (5.33 bits) |
| mean log probability per byte | **−0.8098 nats** | −0.8091 nats |
| byte-normalised perplexity | **2.2474** | 2.2459 |
| average bytes per word | 5.127 | 5.124 |

The average word costs 5.34 bits over 5.13 bytes, i.e. **1.041 bits per byte inside
words** — which is the fitted asymptote from `loss-ceiling.md` (0.722 nats = 1.042
bits). The whole stream costs 1.156 bits/byte. The 0.115 bits/byte difference is what
remains outside word interiors: spaces, capitalisation, punctuation, and choosing which
word comes next. That is the same gap `capability-audit.md` found at word starts
(70.7% accuracy against 76.1% inside words), now measured in bits.

## 4. Empirical word frequency in validation

```
1,266,259 tokens, 8,785 case-folded types
hapax share 23.7% of types
916 types cover 90% of tokens
top: the 69,448 · and 59,887 · to 44,197 · a 40,201 · was 35,149 · he 27,458 · she 26,787
```

Reported separately from model likelihood, as the design requires: frequency is corpus
fact, not a training objective. Its practical consequence is that a model which gets
only the top 916 words right already covers 90% of all tokens it will ever emit — which
is why 74.5% byte accuracy coexists with incoherent stories. Accuracy is dominated by
function words; coherence depends on the long tail.

## Test split: the untouched one

| | validation | test |
|---|---:|---:|
| next-byte cross entropy | 0.803 nats | **0.801 nats** |
| bits per byte | 1.159 | 1.156 |
| argmax accuracy | 74.5% | 74.6% |

Story-aware sampling, 200 batches of 32 windows, seed 4242. The two splits agree to
within 0.002 nats. Two things follow: there is no gap that would indicate the prefix-cut
training slice memorised anything, and the 0.801 measured at the end of training is
reproducible on data this run never touched.

Sample continuations from test-split prompts (temperature 0.8) are in the JSON. They
read as the same voice as the training-split samples, including the same failure mode:
`She pouced one`, `the shop made a funny`, `you is dry or`, `veggatable`.

## Known approximations

- Word metrics tile the file in fixed 256-byte windows, so a window that spans a story
  junction feeds one story's tail as another's context. About one tile in three contains
  a junction, but only the first few positions in it are affected. The loss above does
  not have this problem: it samples story-aware windows, exactly as training did, which
  is why both numbers are reported rather than one.
- The 120-sample validity figure bounds the rate; it does not pin it. A 400-byte sample
  is also short relative to a whole story, and invalidity usually appears mid-story.
